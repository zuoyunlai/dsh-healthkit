## 3. 核实台账（逐条复现 + 判定）

### V01 · R2c 把「取不到证据」报成 MEASURED P0 —— ✅ 成立（P0）

**原断言**：YAML 解析器取不到时，R2c 仍报 `severity=P0` 且 `confidence=MEASURED`。

**复现**：

```js
const f = clone(BASE);
f.patchEntries.desktop = { error: 'YAML_UNAVAILABLE' };   // 取不到解析器时的真实形状
runRules(f, allowlist).filter(x => x.ruleId === 'R2c')
// → [{ sev: 'P0', conf: 'MEASURED', t: 'patch YAML 解析失败：YAML_UNAVAILABLE' }]
```

**影响**：`rubric.caps` 规定「≥1 条未关闭 P0 ⇒ 总分 ≤5.0」。
体检器因为**自己取不到 yaml 模块**，就会把用户的机器判到封顶分——这是把「体检器无能力判断」误报成「用户配置坏了」。
另两种情形（YAML 语法错）报 P0 是**正确**的，不应一并降级。

**修法**：区分错误来源。`error === 'YAML_UNAVAILABLE'` → `severity=P2`、`confidence=UNKNOWN`；
其余解析错误保持 P0。

### V02 · peer 走廊 —— ⚠️ 部分成立，**我原提的修法是错的**（降级 P2）

**原断言**：peer `^0.2.1-rc.1` 与宿主不相交；建议改为 `>=0.2.0-0 <0.3.0-0`。

**核实过程**：

1. `plugin_doctor` 的 X1 确实 FAIL，但它比对的是 **0.2.1-alpha.1 / 0.1.7-rc.2 / 0.0.1-rc.5** 三条**旧基线**，
   而本机真跑的是 **0.2.2-rc.3**（npm dist-tag `next`）——**不是同一个东西**。
2. 用 semver 严格判定 `^0.2.1-rc.1`：

   | 宿主版本 | 来源 | strict | includePrerelease |
   |---|---|---|---|
   | 0.2.2-alpha.3 | npm `alpha` | false | **true** |
   | 0.2.2-rc.1 | npm `latest` | false | **true** |
   | 0.2.2-rc.3 | 本机真跑 | false | **true** |

   → 严格语义下它对**任何**当前宿主线都不成立；插件能跑，**只因为宿主比较是宽松的**（includePrerelease 式）。
   这是实证：11 个工具 + 面板在 0.2.2-rc.3 上正常工作。
3. **我原提的修法是错的**：`>=0.2.0-0 <0.3.0-0` 在 strict 下对上面三条**同样全是 false**（预发布版本要求比较器的
   `[major,minor,patch]` 三元组与版本一致，`0.2.0` 与 `0.2.2` 不同元组即被排除）。**撤回原修法**。
4. 正确的候选（实测矩阵）：

   | 候选 | 0.1.5-alpha.1 | 0.2.2-alpha.3 | 0.2.2-rc.3 | strict | includePrerelease |
   |---|---|---|---|---|---|
   | `^0.2.1-rc.1`（现状） | false | false | false | 全 false | false / true / true |
   | `>=0.1.5-0 <0.3.0-0` | **true** | false | false | 部分 | **三条全 true** |
   | `>=0.2.2-0 <0.3.0-0` | false | true | true | 0.2.2 线 true | true |

5. **这是生态惯例，不是本插件独有**：同宿主的 `dsh-chronicle` 用的正是 `^0.2.1-rc.1`，
   且它的 `@deepseek-ai/dsh` peer 是 `>=0.2.2-0 <0.3.0`。
   本插件**缺** `peerDependencies['@deepseek-ai/dsh']`，只有 `dsh.compatibility.dsh = >=0.2.1-alpha.2 <0.3.0`（strict 下同样不满足 0.2.2-rc.3）。

**修正后的结论**：降级为 **P2（约定脆弱性）**，不是 P0。

**修法**：
- `peerDependencies['@deepseek-ai/dsh']` 补为 `>=0.2.2-0 <0.3.0`（对齐 dsh-chronicle）；
- `peerDependencies['@deepseek-ai/dsh-client-ui-sidebar-right']` 放宽为 `>=0.1.5-0 <0.3.0-0`
  （覆盖 sidebar-right 的 `latest`=0.1.5-alpha.1 与 `next`=0.2.2-rc.3 两条线）；
- 在 `docs/NOTES-host-contract.md` 写明「本插件依赖宿主宽松比较（includePrerelease 式）」这一前提，
  将来宿主若收紧比较，这里会第一个失效。

### V03 · R13 / R17 指纹碰撞 —— ✅ 成立（P1）

**复现**：

```
findings=30  唯一 fp=25
R13: 实例=2 fp=R13  → 退役 1 条实际静音 2 条
R17: 实例=5 fp=R17  → 退役 1 条实际静音 5 条
```

**根因**：`fpOf()` 的 tail 取值只覆盖 `tag / dir / packages[0] / stale[0].entry / dead[0] / profile`。
R13 的 `measured` 里没有这些字段（R17 同理），于是退化成裸规则号 `R13`、`R17`。

**影响**：这直接违背「退役只静音它自己」的语义。用户想退役「web 的 R13」，会连带把「desktop 的 R13」也静音掉——
而这两条的成因完全不同（一个是压缩策略覆盖率低，一个是没声明默认模型）。

**修法**：`fpOf` 的 tail 增加 `m.profile` 兜底；R13 的 `measured` 带上 `profile`；
R17 的 `measured` 带上目录名（现在是 `name` 数组，应改为带 `dir` 的结构）。

### V04 · UNKNOWN 的惩罚轻于已证 P1 —— ✅ 成立（P1）

**复现**：

```
1 条 P1 MEASURED = 9.64
1 条 P1 UNKNOWN  = 9.90     ← 反而更轻 0.26
penalty = { P0: 4.0, P1: 1.8, P2: 0.5, UNKNOWN: 0.5 }
```

**问题**：`rubric.penalty.UNKNOWN` 是一个与严重度无关的固定值。于是「我证实了这是个 P1」与
「我查不出这到底是不是 P1」扣分几乎一样（甚至后者更轻）。

**方向性后果**：一条「取不到证据」的问题会让用户**高估**自己的机器健康度。

**修法**：`penalty.UNKNOWN` 改为「按该条的名义严重度计罚，再乘一个折扣系数」（例如 P1×0.6、P2×0.8、P0×0.8），
保留「取证不足不等于确证」的原则，但不放弃惩罚。

### V05 · 3 个降级场景直接崩 —— ✅ 成立（P1）

**复现**（用夹具逐一退化单个采集源，共测 21 个场景）：

```
CRASH profiles[0].depsNotBundled 缺失 → Cannot read properties of undefined (reading 'filter')
CRASH profiles[0].bakFiles 缺失       → Cannot read properties of undefined (reading 'length')
CRASH profiles[0].bundles 缺失        → Cannot read properties of undefined (reading 'length')
崩溃数: 3 / 21
其余 18 个场景（costTracker=null、yamlAvailable=false、patchEntries 全空、logs={}、machines=null、
disk=[]、capabilities=null、agentPresets=[]、exclusions={} …）均未崩，符合预期。
```

**评价**：这正是 §16.3「删除单采集源必须出 UNKNOWN 而非崩」的验收项——**已声明但未完全实现**。
现有 `test/degradation.mjs` 只测了 4 个「整块消失」的场景，没测「字段级缺失」。

**修法**：`runRules` 入口对每个 profile 做字段默认化（`depsNotBundled ?? []`、`bakFiles ?? []`、`bundles ?? []`），
或让 `collect` 保证这些字段恒在；并把上述 3 例补进 `degradation.mjs`。

### V06 · `allowRepair` 是空壳配置项 —— ✅ 成立（P2）

**核实**：`grep allowRepair index.js src/ bin/ client.js` → **零命中**。该字段只出现在
`cordis.patch.yml`（`allowRepair: false`）与规划/差异文档里。

**性质**：这是**声明与实现不一致**，不是安全漏洞——现状恰恰是最安全的（没有修复能力）。
但它让读者以为「打开 allowRepair 就能让体检器改配置」，而实际无论如何都不会改。

**修法**：二选一——① 实现门控（`audit_clean` 的 apply / `audit_retire` 受它约束）；
② 删掉该字段，并在 `docs/PLAN-DEVIATIONS.md` 记明「只出命令不落盘，无修复开关」。

### V07 · 4 条规则夹具零覆盖 —— ✅ 成立（P2）

**核实**（夹具实际命中 23 条规则）：

| 规则 | 夹具命中 | 原因 |
|---|---|---|
| R18（引擎资产不可回收） | 否 | 夹具 `engineAssets` 为空 |
| R23（bundle 缺 dsh.bundle） | 否 | 夹具没有各 bundle 的 package.json |
| R14b（newly not running） | 否 | 夹具 `logs.notRunning` 为空 |
| R3d（无法读取冷静期豁免） | 否 | 夹具有 exclusions，不走该分支 |

**影响**：这 4 条规则的**判别逻辑从未被测试执行过**。R18 与 R23 还是 P0 级——一条从未跑过的 P0 规则，
其正确性没有任何证据支撑。

**修法**：夹具改为**由真实采集派生**（跑一次 `collect()` 落盘快照当黄金样本，夹具从它裁剪），
而不是手写摘要；或至少补 4 个专门的最小夹具。

### V08 · 无「撤销退役」入口 —— ✅ 成立（P2）

**核实**：`grep unretire|undo|撤销` → 零命中。`audit_retire` 只支持新增记档，
`retirements.json` 一旦写入只能手工删文件。

**影响**：与 §13.7「自审分离」的初衷相悖——记档容易，纠错没有门。误记一条真问题后，
用户只能去翻 JSON。

**修法**：`audit_retire` 增加 `action=restore`（按 fp 撤销），CLI 加 `--unretire <fp>`。

### V09 · `audit_run` 自称「只读」却写两处文件 —— ✅ 成立（P2）

**复现**（实测计数）：

```
调用前：runs=20 份，history.jsonl=40 行
调用 audit_run
调用后：runs=21 份，history.jsonl=41 行
```

写的是：`$DSH_HOME/dsh-healthkit/history.jsonl`（账本）与 `runs/<stamp>.json`（快照）。
**裸 `audit()` 本身不落任何文件**（已单独验证），写入发生在调用层的记账与快照。

**性质**：这是**文案不精确**而非安全问题——插件只写自己拥有的目录，不碰被检对象。
但工具描述写「只读体检：不修改任何配置、不联网」，读者合理理解为「不产生任何副作用」。

**修法**：描述改为「只读体检：只读取被检对象；会向插件自己的数据目录写入一条账本与一份快照（可关）」，
并给 `audit_run` 加 `record=false` 参数。

### V10 · 报告不区分「已修好」与「被静音」 —— ✅ 成立（P3）

**核实**：报告 `## 三之三、已退役（误报记档，不计分）` 只列退役项；没有「这条消失了是真修好了还是被静音了」的区分。
而 `audit_diff` 已经能算出这个三分（新增 / 真修好 / 新退役），只是两者没有打通。

**影响**：分数上升时无法判断「我修好了 3 条」还是「我静音了 3 条」——而这两者的健康度含义完全相反。

**修法**：把 `audit_diff` 的三分并进报告「三之三」段。

### V11 · 清理护栏的 `data` 规则靠字面量 —— ❌ **撤回**（我原判不成立）

**原断言**：护栏用正则 `[\/]data([\/]|$)`，应改为路径分段判断，否则跨平台不一致。

**核实**（正则法 vs 分段法，5 组用例含 POSIX 路径）：

```
C:/u/.dsh/data/db                正则=true  分段=true
C:/u/.dsh/metadata/x             正则=false 分段=false
C:/u/.dsh/attachments/y          正则=true  分段=true
C:/u/.dsh/my-data/x              正则=false 分段=false
C:/u/.dsh/cache/dsh-image-gen    正则=false 分段=false
/home/u/.dsh/data/db             正则=true  分段=true
/home/u/.dsh/metadata/x          正则=false 分段=false
/home/u/.dsh/data                正则=true  分段=true
```

两种方法**结论完全一致**，且 `[\/]` 本身已跨平台。**原判为过度解读，撤回。**
（我最初只测了 Windows 路径就下了结论——这正是「取证不足就下判断」的典型反例。）

## 5. 结构性问题（不计入上表，属方向性意见）

### 5.1 三分之二火力在「配置自洽」，不在「配置是否好用」

按**去重规则号**统计：consistency 10 / plugins 7 / security 6 / disk 4 / reliability 4 / context 2 / modelCost 2，合计 35。
其中三分之二是「配置面是否自洽」类。

对照 rubric 权重与规则数的比值（权重 ÷ 规则数）：

| 维度 | 权重 | 规则数 | 每条规则承载的权重 |
|---|---|---|---|
| modelCost | 15% | 2 | 7.5% |
| context | 5% | 2 | 2.5% |
| security | 25% | 6 | 4.2% |
| disk | 10% | 4 | 2.5% |
| reliability | 10% | 4 | 2.5% |
| plugins | 15% | 7 | 2.1% |
| consistency | 20% | 10 | 2.0% |

**modelCost 用 15% 的权重押在 2 条规则上**，而这 2 条恰好是自动判定最弱的（R11 依赖记账文件新鲜度、
R12 依赖声明值与运行时一致——后者源码自己标了 `UNKNOWN`）。consistency 则是 10 条规则分 20%。

建议：把 weight 从「维度 × 规则数」改为「维度 × **判别力**」——即该维度里有多少条规则能给出确定结论。

### 5.2 分数波动来自宿主，不来自用户

审计期间实测到分数从 **8.36 → 9.6 → 9.78** 的变化。核查证据：两个 profile 的 `cordis.patch.yml`
的 mtime 均为**宿主启动时刻**（21:00），且插件源码**从不写** `cordis.patch.yml`
（`grep -rn writeFileSync src/` 只命中 retirements / history / runs / trash manifest / probe 临时 profile）。

即：**宿主启动时会重写用户的 patch 文件**，手改 patch 的内容不一定能存活。
这对体检器有两个含义：① 任何分数都是快照，不宜当趋势基线；② 「手改 patch」这条路不可靠——
体检器给出的修法应当指向**宿主原生机制**（如 `dsh plugin --profile <p> add/remove`），而不是直接编辑 patch。

### 5.3 唯一真正拉开差距的方向：跨重启自证

PLAN §11 里唯一没做、且**不与「只读审计」定位冲突**的高价值项是「修复后自动验回」。
现状是：体检器已经具备快照（`runs/`）、退役（`retirements.json`）、差异归因（`audit_diff`）三块拼图，
只差最后一步闭环——**在重启后自动比对快照、重跑相关规则、发现回归就报警**。

市面上同类体检插件大多停在「告诉你有问题」；能自动验证「修好了没有」的极少。
这是这个插件最有机会做出差异化的方向。

**但必须守住一条**：`cordis.patch.yml` 的语义是**整段替换**不是深合并，写错一个字段就是整个配置面塌掉。
所以跨重启自证应做成「**只出 diff + 预检 + 用户确认后由宿主原生机制落盘**」，绝不自己写 patch 文件。
