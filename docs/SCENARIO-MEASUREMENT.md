# 场景判据实测（2026-11-16）——结论：**不做**

> 对应 PLAN §5「路径启发 scenarioHint」。规划原文即标注该组判据为
> 「推想的、未实测」。本轮按纪律实测一遍，结论是**在真实目录结构上不成立**。

## 实测方法

扫描本机真实项目目录（排除 `node_modules` / `.git` / 各种构建产物），
逐目录判定规划里给的三组特征，统计命中率与相互重叠。

- 扫描根：`E:/Documents/deepseek-harness`、`E:/Documents`、`E:/HERNESS`
- 扫描深度：2 层子目录
- 去重后目录数：**1349**
- 复现脚本：`/e/auditkit-boot-home/probe-scenario.mjs`（只读）

## 结果：命中率约 0%

| 规划里的判据 | 命中 |
|---|---|
| code：`package.json` + `src/` | 2 / 1349（0%） |
| code：再加 `test/` 目录 | 2 / 1349（0%） |
| design：`*.psd` / `*.fig` | 2 / 1349（0%） |
| design：`tokens.json` | 0 / 1349（0%） |
| writing：`run/` 目录 | 3 / 1349（0%） |
| writing：再加「证据包 / evidence」 | 0 / 1349（0%） |
| （参考）文档类：docx/pptx/xlsx/pdf | 76 / 1349（6%） |

**1345 个目录一个都不命中。** 特征之间没有重叠（code∩design = 0、code∩writing = 0、
design∩writing = 0）——不是「重叠误判」，是「几乎不触发」。

**关键事实**：本机 76% 的目录既没有 `package.json` 也没有 `src/`，24% 是「一堆 md 文件」——
这类目录正是论衡、审计报告、评审台账的实际形态。规划里给 writing 场景的判据
（`run/<项目>/*.md` + `证据包/`）只命中 3 个目录，说明它**描述的是一个理想化的目录结构，
而不是用户真实的组织方式**。

## 结论与处置

**不做路径启发。** 理由三条，按重要性：

1. **判据在真实数据上不成立**（0% 命中率）——写进代码就是一段永远不触发的死代码，
   或者更糟：偶尔在某个目录误触发，给出错误的场景建议。
2. **收益低于替代方案**：用户手动指定 `scenario` 就是一个参数的成本，
   而错误的自动猜测会污染 ADVISORY 段——而 ADVISORY 段本来是给人参考的，
   掺进错的东西会让整段可信度下降。
3. **和已有的 `--init` / `audit_capabilities` 重叠**：那两处已经回答了
   「你有什么、缺什么、怎么补」，场景猜测只是再加一个低可靠度的维度。

**如果将来真需要场景感知**，正确的做法不是猜路径，而是：
让用户在工作区里放一个声明文件（如 `.dsh-healthkit.json` 写 `{"scenario":"code"}`），
或者在 agent preset 里声明场景——**显式优于猜测**，这与本插件一贯立场一致
（路径启发本来就不计分，只作提示；既然连提示都不准，不如不要）。

## 与规划差异文档的对应

PLAN-DEVIATIONS.md 的「明确不做」第 3 条（路径启发 scenarioHint）此前写的是
「原规划给的判据是推想的，未实测」。本轮把**未实测**补成了**已实测且不成立**，
并附上命中率数字与复现脚本。
