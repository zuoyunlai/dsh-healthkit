# dsh-auditkit 实施规划（2026-11-16 · v1 定稿）

> **实施后的差异说明见 [PLAN-DEVIATIONS.md](./PLAN-DEVIATIONS.md)** —— 哪些章节已补齐、哪些明确不做、每条附实测依据。本文件保留原始规划内容作为对照。

> 状态：设计已收敛，待开工 P1。本文所有宿主结论分两类标注：**［实测］** 为本机当日可直接复核的证据；**［推断］** 为未验证假设，P1 必须先验证再依赖。

## 0. 一屏摘要

- **它是什么**：跑在 DSH 宿主内部的**整机体检器**。只读审计配置面 / 装载面 / 权限面 / 模型与成本 / 上下文预算 / 磁盘构成，给出可复算的评分、带证据的问题清单、可执行的修复补丁，并按**能力缺口**给出配置优先的补强建议。
- **它不是**：不是 `plugin_doctor`（后者判单个插件仓库合规）；不是插件市场（不安装、不排名）；不是自动运维（不重启宿主、不自动装包）。
- **差异化的两颗钉子**：① 结论可**退役**（误报必须能记档并永久抑制）；② 修复可**跨重启自证**（宿主重启后自动验回，回归则回滚）。
- **形态**：插件（宿主内，能看活状态）+ CLI（`npx dsh-auditkit init`，服务首装零插件场景）。
- **包名**：`dsh-auditkit`（备选 `dsh-physician` / `dsh-healthcheck`）。npm 实测：`dsh-audit` 与 `dsh-shenji` 返回 HTTP 200（已被占用），上述三个返回 404（可用）［实测］。

## 1. 自建必要性

| 已有能力 | 覆盖什么 | 本插件是否重复 |
|---|---|---|
| `@perrylink/dsh-plugin-doctor` | 单插件仓库的 R/K/X 组契约与补丁可定位性，pass/fail | 不重复，且应作为修复后的下游自检 |
| `dsh-find-plugins` / `dshmarket` | 发现与安装 | 不重复；本插件只给候选与代价，不执行安装 |
| 人工审计（2026-11-16 两轮） | 能出结论，不可持久、假阳性无记忆 | 本插件把这条路径固化 |

空白点不在「能不能查」，而在**结论没有生命周期**：一条判断应能处于 `open → fixed → verified` 或 `retired(误报)`，且退役原因留档。2026-11-16 的手工审计里出现 3 条自证错误的结论（依赖数 10→11、provider 块「已漂移」实为同步、web 树可当 desktop 预检实为不可），这正是需要机制化的地方。

## 2. 已实测的宿主事实（设计所依赖）

1. 配置层级为 **bundle → profile → home → CLI** 四层；patch 语义是**整段替换**（`A patch config replaces the whole config`），不是深合并；存在 include-local patches［实测：`--dump-config-schema` 原文］。
2. `~/.dsh` 根部当前**没有** home 层配置文件［实测］。
3. `dsh --profile desktop --dump-config` 被拒（`profile "desktop" is managed exclusively by the Electron application`）［实测］。**故插件必须在宿主内读状态，不能靠外部 CLI 审计 desktop。**
4. 任意 profile 可用 `--patch <file> --dump-config` 静态展开；patch 只能定向**已存在**的 id，不能新增 bundle（对不存在的 id 报 `entry "X" not found`）［实测］。
5. bundle 的贡献可用「最小 probe profile」枚举：只装 base + 目标 bundle，dump 后按 `# == <bundle>` 分段读取［实测：本次用它确认 inspector bundle］。
6. `@deepseek-ai/dsh-experimental-inspector-profile` 贡献 3 个条目：`experimental-inspector`（`@deepseek-ai/dsh-experimental-inspector`，config `captureFetch: true`）、`session-inspector`、`client-ui-stats`。desktop 里被 `disabled: true`［实测］。**它更像「会话/网络/UI 观测」而非「配置树读取器」**——我原先假设它是配置读取面，这条降级为［推断］，不可作为 P1 依赖。
7. 插件契约：模块导出 `name` + `apply(ctx, config)`（可选 `inject`）；一切注册走 `ctx.effect()/ctx.on()`；扩展点强弱序 `tools.restrict() < tools.guard() < waterfall < system-prompt/assemble`；可选服务用 `ctx.get(name)`，未 inject 直接访问会静默杀掉整个插件［实测：dsh-primer 契约，本机 2026-11-09 曾因它丢 2 个工具］。
8. 宿主桌面 crash 日志位于 `%APPDATA%\@deepseek-ai\dsh-desktop\logs\crash-*-{host,main,web-boot}.log`；本机现有 4 个，`skipping profile bundle` / `incompatible` 命中 **0** 条［实测］。
9. 包操作唯一可用通道 `dsh plugin --profile <p> add|remove`（内部 pnpm 11.28.5）；shell 里的 pnpm 是空壳［实测］。
10. 凭据栅栏只存在于 ops 文件工具层（读 `.credentials.yaml` 返回 `CREDENTIAL_DENIED`），同进程 shell 不受限［实测］。

## 3. 核心设计原则（每条附违反后果）

1. **只读默认，修复显式**：`allowRepair` 默认 false。违反后果：一个能改配置的插件会放大既有的全盘权限爆炸半径。
2. **每条结论带可复算证据**（文件:行 / 实测值 / 命令回执）。违反后果：三个月后清单变成无人敢动的噪音。
3. **规则必须能报 UNKNOWN**，而非猜。违反后果：误报摧毁信任，比漏报更坏。
4. **评分是数据不是代码**（rubric.yaml 带版本号）。违反后果：跨时间不可比。
5. **「可回收」与「无上限」必须分开报**。违反后果：制造零收益清理动作（2026-11-16 已踩：附件 201M 在 30/60/90 天口径下可回收 0MB）。
6. **引擎资产不得判为垃圾**：内容寻址的解包产物（同目录有 `provenance.json`、单一 hash 子目录）是运行时本身的成本。违反后果：把 bash 引擎删掉（2026-11-16 已踩：`dsh-ops/shells/niubash-prepared` 108M 是 niubash 解包）。
7. **价值判断不自动化**：权限档位、私钥位置、记忆层取舍、保留策略只出建议与代价对比；自动修只允许「机械一致性」。
8. **建议与评分物理隔离**：`ADVISORY` 结论永不进入分数。违反后果：体检的可信度来自可复算，主观推荐混入即废。
9. **不挑宿主**：见 §13。

## 4. 能力缺口模型（本轮核心新增）

### 4.1 判定单位是「能力域」，不是「插件名」

插件会改名、下架、被替代；能力不会。故所有补强建议都以能力域为单位，插件只是**补救手段之一**。

| 能力域 | 判定信号（示例） |
|---|---|
| 模型路由 | 可路由 provider 数 vs 模型目录条目数 |
| 会话持久化 | session 服务与持久化条目是否挂载 |
| 文件与 shell | 工具面是否存在、shell 是否可用 |
| 检索（web） | 搜索/抓取工具、引擎池与兜底顺序 |
| 记忆（短期） | 热记忆条目与会话注入 |
| 记忆（长期/项目） | 索引与 recall 工具、索引体积 |
| 上下文预算 | compaction 策略覆盖率 |
| 图像生成 | 已配置 provider 数与可达性 |
| 视觉理解/OCR | vision 工具面 |
| 文档产出 | office/pdf 类工具 |
| 浏览器自动化 | 浏览器工具与登录态 |
| 远程/SSH | 机器注册表与密钥可用性 |
| 任务编排 | 自动化/定时条目 |
| 成本可见性 | 记账文件新鲜度 |
| 安全边界 | 权限档位、凭据栅栏、域名白名单 |
| 代码工程 | git/测试/格式化能力 |
| 长文写作 | 长文类技能与流水线 |
| 音视频 | ffmpeg/tts 类能力 |
| 数据与图表 | 图表/渲染工具 |
| 主题与可用性 | 主题/布局插件 |

### 4.2 六种状态（缺口不等于缺失）

`present` / `missing`（没装）/ `redundant`（装多了，互相打架或重复注入）/ `degraded`（装了但失效：无凭据、停更、schema 报错）/ `conflicting`（两个实现抢同一工具位）/ `unknown`（取不到证据）。

**冗余与冲突同样是缺口**。2026-11-16 本机实例：记忆能力 `redundant`（4 套同时每轮注入，≈5k token/轮）、抓取能力 `conflicting`（`fetchProviderTakeover: true` 与 `web.fetchProvider` 并存）、模型能力 `degraded`（28 个模型声明、1 个 provider 可路由）。

### 4.3 补救阶梯：配置优先

每个缺口给**有序**的补救方案，顺序固定为：

1. **配置（config）**——改现有条目的 config，零新增依赖
2. **模型/provider**——换路由、补 apiKeyEnv/baseURL
3. **插件（plugin）**——仅当 1、2 都无法补上时，才指向市场候选
4. **习惯（habit）**——流程约束，如「陌生项目用 workspace-write 起会话」

**硬规则**：任何指向「装插件」的建议，必须写明「为什么只用配置补不上」。写不出这一句，就不许出这条建议。

### 4.4 推荐实体

    Recommendation{
      capability, state, gapKind: missing|redundant|degraded|conflicting,
      remediations: [ { kind: config|provider|plugin|habit, action, cost, benefit, risk } ],
      market: [ { name, source, verifiedAt, why, confidence } ],   // 仅当 kind=plugin 时出现
      confidence: MEASURED | ADVISORY
    }

`market` 的数据源：`<profile>/.dsh-market/snapshots/*.json`（dshmarket 已挂载，目录实测存在，schema 未验证 → ［推断］）；npm registry（当日实测可达）。每条候选必须带 `verifiedAt` 与 30 天 TTL，过期降级为提示。

## 5. 场景与路径启发

- 档位：`general`（默认）/ `code` / `design` / `writing`。
- 优先级：配置 `scenario:` > 工具参数 `audit_run scenario=` > **路径启发（只作提示）**。
- 路径启发输出 `scenarioHint{ scenario, confidence, evidence }`，**只进 ADVISORY 段，永不进评分**。证据示例：`package.json+src/` → code；`*.psd/*.fig/tokens.json` → design；`run/<项目>/*.md`+`证据包/` → writing。
- 启发失败或低置信 → 回 `general` 并说明原因，不硬猜。

## 6. 架构与数据流

    采集 collectors/  （只读；每采集器独立 try/catch；产出 Fact + 来源 + 时间戳）
      ↓ Facts（可落盘、可 diff、可重算）
    规则 rules/       （Rule = {id, dimension, severity, detector, evidence, retireWhen, knownFalsePositives}）
      ↓ Findings（带证据链与置信度）
    评分 rubric.yaml  （维度权重 + 硬上限 + 场景覆盖 + 版本）
    缺口 capabilities.yaml（能力域 → 信号 → 补救阶梯）
      ↓ Score + Recommendations
    修复 fixers/      （L1 建议 / L2 配置补丁 / L3-plan 出命令；声明 touchedPaths/reversible/restartNeeded/verifyCmd/preflight）
    验证 verify/      （重启后 boot hook 自动比对 snapshot，回归则回滚）

采集与规则**解耦**：同一份 Facts 快照可反复重算规则，避免边测边改口径。

## 7. 目录布局

    ~/.dsh/dsh-auditkit/            # 插件私有（可删可重建，禁止手改）

## 8. 数据模型

- `Fact{ id, source, collectedAt, value, unit, evidence{file,line,cmd,sha} }`
- `Finding{ id, ruleId, dimension, severity, title, claim, evidence[], measured{}, falsifiableCheck, status, retireReason?, firstSeen, lastSeen }`
- `Rule{ id, dimension, severity, requiresFacts[], retireWhen, knownFalsePositives[] }`
- `Rubric{ version, dimensions[{key,weight}], caps[{when,maxScore}], scenarios{} }`
- `Recommendation` 见 §4.4；`FixPlan{ findingId, level, touchedPaths[], diff, reversible, restartNeeded, preflight[], verifyCmd }`

## 9. 规则清单（R1–R18）

一致性：R1 依赖∖bundles 差集（支持白名单+理由）；R2 patch 中 `disabled` 的 id 是否存在于组合树；R3 `minimumReleaseAgeExclude` vs 实装版本；R4 profile 内 `.bak`/副本堆积（排除自身报告）；R5 配置是否纳入 VCS；R6 多 profile 漂移（providers 段已有 `sync-providers.mjs` 可复用）。

安全：R7 权限档位 × approval 组合；R8 凭据栅栏是否只在工具层；R9 外部密钥/私钥位置与权限；R10 高危扩展面是否全放行（`allowedUrlHosts` / `blockedDomains`）。

运行与成本：R11 成本记账新鲜度；R12 声明值 vs 运行时注入值；R13 compaction 覆盖率；R14 装载日志中的 `stand-in module` / `newly not running` / schema 错误；R15 已挂载插件数 vs bundles 数。

磁盘与上下文：R16 每轮固定注入占比；R17 **「可回收」与「无上限」分离**（报 `oldestAge` / `reclaimAt30_60_90d` / `growthPerWeek`）；R18 **引擎资产识别**（内容寻址解包产物 + provenance.json → 判为不可回收）。

全部规则需同时具备：机械检测器、证据形态、退役条件、已知假阳性样例。缺一不许合入。

## 10. 评分模型

- 维度与默认权重：安全 25 / 一致性 20 / 模型与成本 15 / 插件能力 15 / 可靠性 10 / 磁盘 10 / 上下文效率 5。
- **硬上限**：存在未关闭 P0 → ≤5.0；P0 ≥3 → ≤4.0；某维度 `UNKNOWN` 覆盖 >30% → 该维度 0.6 折扣并标 `reduced-confidence`。
- **场景覆盖**：`code` 档提高一致性与上下文预算权重（各 ≥25%）；`writing` 档上下文效率 ≥25%；`design` 档图像与视觉权重上调。总分必须标明所用档位与 rubric 版本。
- 输出：总分 / 分维分 / **封顶原因** / rubric 版本 / 与上次的差值与变动归因。
- 基线：2026-11-16 本机 4.25/10（能力 7.0、工程 3.8），3 个 P0 命中 ≤5.0 上限——可直接作为回归黄金样本。

## 11. 修复引擎

- **L0** 只报告（默认）；**L1** 出 diff 不落盘；**L2** 应用配置补丁（先 git snapshot，再 `frozen-lockfile` 预检、`yaml.parse` 校验）；**L3-plan** 只产出 `{cmd, preflight, expectedEffect, rollback}`，**永不执行**（本轮决策）。
- 不可自动：重启宿主、改权限档位、移动外部凭据（L4 明确不做）。
- **跨重启闭环**：L2 后写 `pending-verify.json` → 用户重启 → boot hook 比对快照、重跑相关规则、扫描装载日志新增异常 → 全绿标 `verified`，有回归则自动回滚并标 `regressed`。
- 工具面：`audit_run` / `audit_report` / `audit_findings` / `audit_explain` / `audit_retire` / `audit_plan_fix` / `audit_verify` / `audit_score` / `audit_capabilities`。

## 12. 工具与权限

- 全部工具默认挂 `read-only` 语义；写操作只在 `allowRepair: true` 且单次带确认时可用。
- 读凭据一律走凭据栅栏语义（拒绝即报 `BLOCKED_BY_CREDENTIAL_FENCE`，不绕过）。
- 不新增网络出站：市场数据只读本地快照；npm 查询仅在用户显式要求时进行。

## 13. 通用性约束（不挑宿主）——硬要求

1. **不写死 profile 名**：从 `~/.dsh/profiles/*` 枚举，禁止出现 `desktop` / `web` 字面量做分支。
2. **不写死路径**：只用 `DSH_HOME`、`os.homedir()`、会话 cwd 推导；禁止出现 `E:\`、`C:\Users\<name>` 之类。
3. **跨平台**：Windows 的 niubash、macOS/Linux 的 shell 后端差异一律抽象为「shell 是否可用」，不做文本级特判；R18 用「provenance.json + 单一 hash 子目录」这一**结构特征**识别引擎资产，而不是认目录名。
4. **宿主版本无关**：bundle id / 条目名不硬编码；取不到就 `UNKNOWN`。bundle 贡献用 §2.5 的 probe 法动态枚举。
5. **插件名不硬编码**：能力标签来自 `capabilities.yaml` + 关键词草稿，允许用户覆盖；自动标签只作草稿（预计错误率 ≥20%）。
6. **无 GUI / 无历史也能跑**：CLI 形态不依赖宿主服务；插件形态在缺服务时降级而非崩（`ctx.get()` 判空，禁止裸 `ctx.x`）。
7. **自审分离**：报告单列 `self` 段（本插件自身状态），不参与评分。

## 15. 分阶段实施

### P1 只读审计 + 评分 + 首装探测（4 天）
交付：采集器骨架（配置/装载/工具面/磁盘/日志 五类）+ 规则 R1/R2/R3/R5/R7/R11/R15/R17/R18 + `rubric.yaml` v1 + Markdown 报告 + 首装探测。
验收：① 对 2026-11-16 黄金基线，3 个 P0 复现 ≥2、11 条 P1 复现 ≥9、假阳性 ≤10%；② 必须把「附件可回收」「dsh-ops 是垃圾」判为**非发现**；③ 老机器首装探测必须返回 `not-fresh`；④ `allowRepair:false` 下任何写操作被拒（含 dryRun）。

### P2 证据链 / 退役 / 跑分对比（2 天）
交付：Finding 生命周期、`audit_retire`（原因必填）、两次跑分差异与归因。
验收：能把 2026-11-16 的三条自证错误录成 `retired`，且规则改动后仍判非发现（fixture 守护）。

### P3 修复 L1/L2 + L3-plan（4 天）
交付：patch 条目增删、`.bak` 归档、VCS 初始化、exclusion 收敛、依赖差集命令生成；git 快照与一键回滚。
验收：任一 L2 后 `git diff` 可读、`frozen-lockfile` 通过、`yaml.parse` 通过、回滚一条命令完成；L3-plan 的 preflight 必须能拦住已知坑（差集非 0、锁文件不一致、YAML 不合法）。

### P4 能力缺口 + 场景 rubric + 推荐（5 天）
交付：`capabilities.yaml`（20 域）、六状态判定、配置优先补救阶梯、场景权重覆盖、`ADVISORY` 隔离。
验收：同机三档场景总分差异只来自 rubric 权重；`ADVISORY` 项零进入评分（断言测试）；每条「装插件」建议都带「为什么配置补不上」；市场快照缺失时降级为 `unknown` 而不崩。

## 16. 测试计划

1. **黄金基线**：`fixtures/baseline-2026-11-16.json`（本轮两批实测数据）驱动全规则回归。
2. **假阳性专区**：每个 `retired` 项一个 fixture，规则改动后必须仍判非发现。
3. **降级**：删除单采集源（模拟宿主升级），必须出 `UNKNOWN` 而非崩或误报。
4. **权限**：`allowRepair:false` 时写操作全拒。
5. **通用性**：路径/平台/版本三维参数化——把 `DSH_HOME` 指到临时目录、把 profile 名改掉、把 bundle 列表换掉，仍应跑通。
6. **端到端**：`audit_run → plan_fix → apply(config) → 重启 → verify`，含一次人为破坏触发的自动回滚。

## 18. 风险登记册

| 风险 | 触发 | 影响 | 缓解 |
|---|---|---|---|
| 规则漂移（宿主升级） | 采集器抛错率上升 | 误报或漏报 | 每采集器独立 try/catch、`UNKNOWN` 降级、采集器 self-test |
| 修复打坏启动 | L2 后重启失败 | 用户无法使用 | snapshot + frozen 预检 + boot 自检 + 自动回滚 |
| 成为攻击面 | 插件能写配置 | 放大权限风险 | `allowRepair` 默认 false、复用凭据栅栏、不做 L4 |
| 自我审计悖论 | 插件本身可被审计 | 结论不可信 | `self` 段单列且不计分 |
| 误报摧毁信任 | 规则粗糙 | 用户弃用 | `retire` 机制 + 假阳性率作为发布门槛（>10% 不发） |
| 推荐腐烂 | 插件改名/下架 | 建议失效 | `verifiedAt` + 30 天 TTL 降级 |
| 体检变导购 | 推荐带权重/排序 | 公信力崩塌 | 无付费排序、无「必装」、不自动安装 |
| 场景误判 | 路径启发猜错 | 建议错位 | 只作提示、不进分数、默认 general |
| 首装无插件可用 | 鸡生蛋 | 引导不可用 | CLI 形态承担，插件形态不承诺 |

## 19. 明确非目标

不做单插件仓库合规审计（交 `plugin_doctor`）；不自动重启宿主；不自动执行包操作；不联网上报；不做历史 `run/<项目>` 追溯；不引入 ML 打分；不做多机同步；不接管市场安装界面；不做「一键套用场景配置包」。
