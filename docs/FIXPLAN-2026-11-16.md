## 1 B-1 ｜ R9 外部私钥（可变，且比预想的简单）

### 实测事实

| 项 | 值 |
| --- | --- |
| 引用它的机器 | `m-mwdc5uj0-28mp`（47.107.230.73），`useSshConfig: false` |
| 注册表里的路径 | `F:\Downloads\_本地ssh.pem` |
| 该文件 mode | **`-rwxrwxrwx`**（人人可读写） |
| 该文件 ACL | 继承而来，**含第二个账户 SID `-1006` 的 `(I)(RX)`** —— 别人能读 |
| 大小 / mtime | 1702 B / 2026-11-12 16:38 |
| `~/.ssh/47.107.230.73.pem` | 1702 B / 2026-11-12 17:13 |
| **两者 sha256** | **`6bcbdfe1…8ab7` 完全相同** |
| 后者 ACL | `SYSTEM / Administrators / Zuoyunlai` 三条，**未继承**，干净 |

### 结论

**不需要搬密钥。** 同一把私钥已经以正确权限躺在 `~/.ssh/` 里了，
Downloads 那份是 35 分钟后多出来的一份「野拷贝」。

修法 = 把注册表指向 `~/.ssh` 那份 → 验证连通 → 删掉 Downloads 那份。
密钥材料零搬运，连接零风险。

### 命令

**① 备份注册表**

```bash
cp ~/.dsh/remote-workspaces/machines.json \
   ~/.dsh/remote-workspaces/machines.json.bak-$(date +%Y%m%d-%H%M%S)
```

**② 改引用**（存成 `fix-r9.mjs` 再跑，避免命令行引号地狱）

```js
import fs from 'node:fs'; import path from 'node:path'; import os from 'node:os';
const p = path.join(os.homedir(), '.dsh', 'remote-workspaces', 'machines.json');
const target = path.join(os.homedir(), '.ssh', '47.107.230.73.pem');
if (!fs.existsSync(target)) throw new Error('目标不存在: ' + target);
const j = JSON.parse(fs.readFileSync(p, 'utf8'));
let n = 0;
for (const m of j.list || []) {
  if (m.privateKeyPath && /Downloads/i.test(m.privateKeyPath)) { m.privateKeyPath = target; n++; }
}
fs.writeFileSync(p, JSON.stringify(j, null, 2) + '\n');
console.log('rewritten=' + n + ' target=' + target);
```

```bash
node fix-r9.mjs
```

**③ 验证**（真连一次，确认还能登）

```
rw_connect({ machineId: "m-mwdc5uj0-28mp" })
```

**④ 连通后再删野拷贝**

```bash
rm '/f/Downloads/_本地ssh.pem'
```

### 回滚

```bash
cp ~/.dsh/remote-workspaces/machines.json.bak-<时间戳> ~/.dsh/remote-workspaces/machines.json
```
（Downloads 那份删了就没了，但它和 ~/.ssh 那份字节相同，**没有信息损失**。）

## 2 B-2 ｜ R7a 权限档位（这条要你拍板，不是修法问题）

### 实测事实

`~/.dsh/profiles/desktop/cordis.patch.yml` 第 221–234 行：

```yaml
- id: permission
  name: "@deepseek-ai/dsh-permission-presets"
  config:
    presets:
      read-only:        { sandbox: read-only,        approval: ask  }
      workspace-write:  { sandbox: workspace-write,  approval: ask  }
      danger-full-access: { sandbox: danger-full-access, approval: never }
    defaultPreset: danger-full-access          # ← 就这一行的问题
```

### 关键判断：改成 workspace-write 会打断你现在的用法

本会话的工作目录是 `E:\Documents\deepseek-harness\default-workspace`，而**今天这一整场工作**改的是：

- `C:\Users\Zuoyunlai\.dsh\profiles\desktop\*`（profile 配置）
- `E:\Documents\deepseek-harness\plugins\dsh-auditkit\*`（插件源码）

两者**都在 session workspace 之外**。切到 `workspace-write` 后，写出范围就只剩 workspace 内 ——
上面这些维护动作会全部需要放行。

**更要命的一层**：本会话的审批提示是关闭的（「需要审批的动作会被自动拒绝」）。
所以收窄后不是「弹窗问你」，而是**直接失败**。
⇒ 若要收窄，必须同时在 GUI 里把审批提示打开，否则等于把维护会话废掉。

### 三个选项（各有明确代价）

| | 动作 | 分数 | 日常影响 | 风险面 |
| --- | --- | --- | --- | --- |
| **A** | `defaultPreset: workspace-write` + **打开审批提示** | 5 → 7.49 | 工作区内写零影响；动 ~/.dsh 或插件源码时弹一次 | 最小：危险动作有人拦 |
| **B** | 保持 `danger-full-access`，只把该档 `approval: never` → `ask` | 5 → 7.49 | 同上（仍需开审批提示，否则自动拒绝） | 次之：沙箱仍全开，但危险动作会问 |
| **C** | 不改配置，**显式退役 R7a**（`--retire R7a --reason "..."`） | 5 → 7.49 | 无 | 原样：零闸门，但台账里写明「已知并接受」 |

### 我的建议

**A**，因为 A 把「今天这种维护会话」变成显式动作而不是默认状态。
今天这一场我改了多少 C: 盘和 E: 盘的配置文件，你一次都没被问过 —— 这不是能力，这是没有闸门。

但 A 的前提是你愿意开审批提示。**不愿意开审批提示的话，A 和 B 都会退化成「静默拒绝」，那就应该选 C**，
诚实地把这档记成「已知并接受的风险」，而不是假装修好了。

## 3 A ｜ 装载面瘦身（结论：现在别动）

### 实测代价

| 项 | 数值 |
| --- | --- |
| bundles 总数 | **40** |
| 配置树顶层条目 | **199** |
| 其中来自宿主安装（`dsh-base` 71 + `dsh-web-app` 95） | **166（83%）** |
| 来自 profile 侧插件 | ~33 |
| profile 侧 30 个插件包占盘 | **249 MB** |

占盘 TOP：`dsh-ops` 86M · `dsh-image-gen` 36M · `dsh-better-sidebar` 20M ·
`dsh-pet-plugin` 17M · `archify` 17M · `dsh-primer` 14M · `genui` 13M · `agency-agents` 10M

### 两个必须先分清的事实

**① 关 bundle ≠ 省磁盘。** 把某个包从 `dsh.profile.bundles` 里去掉，只是少加载它的条目；
它仍留在 `dependencies` 里、仍占 `node_modules`。真要省盘得同时从 dependencies 删掉并重装。
这是两件事，别混着承诺。

**② 核心 166 条不可动。** `dsh-base` / `dsh-web-app` 来自宿主安装目录（profile 里 0 MB、非依赖），
删一个就废掉整个宿主。

### 可关候选（只有两个，且收益很小）

| 候选 | 依据 | 预期收益 |
| --- | --- | --- |
| `@deepseek-ai/dsh-experimental-auto-review` | 无任何可见工具/面板/设置项对外暴露 | 少 1 个条目 |
| `@deepseek-ai/dsh-experimental-ralph-bundle` | `ralph` 工具存在，但你的历史里没有一次 Ralph 循环调用 | 少 1 个条目 + 一个工具位 |

其余 30 个包**每一个都对应着正在用的能力**（工具、技能、面板、模型路由），删任何一个是净损失。

### 测量局限（必须说明）

`--dump-config` 的分节头是「layer 链」（如 `dsh-base, patched by dsh-unlag`），不是「一个 bundle 一节」，
所以**逐 bundle 的条目数无法可靠拆分**。上表的 199 是顶层条目总数（可靠），
但「某个包贡献了几条」我不给数字 —— 给了也是假的。

### 结论

**P4 的正确产出是一张「不值得动」的判断，不是一张待办清单。**
驱动瘦身的应该是「某个插件确实不用了」，而不是「数字想变小」。

真要动，用这个协议（一次只动一个包）：

```bash
# ① 从 bundles 列表移除（不要动 dependencies）
#    编辑 ~/.dsh/profiles/desktop/package.json 的 dsh.profile.bundles
# ② 重启宿主，确认没有工具/面板消失
# ③ 若出问题：把那一行加回去，重启
```

### 5.3 为什么比预测高 0.87 —— 归因工具的局限（重要）

`attribution()` 算的是「**这条结论消失**会怎样」，不是「**改掉它的根因**会怎样」。

R8（`凭据文件对同进程 shell 可读`）的判定条件是 `permPreset().preset === 'danger-full-access'`
（`src/rules.mjs:175`）。所以把默认档位收窄之后，**R7a 与 R8 一起消失** —— 改一个因，掉两条结论。

⇒ 单条反事实给出的是**下限**，真有连锁时实际收益会更高。这条要写进工具的说明，
不能让「+0.87」被读成 bug。

### 5.4 验证过程中的两个自查失误（记下来防复发）

1. **拿旧 dump 文件核对合成树**：`probe1` 有自己的 `cordis.patch.yml`/package.json 副本，
   改 desktop 不影响它。看到 `defaultPreset: danger-full-access` 是旧文件的残影，不是没生效。
   核对合成树前必须先把 desktop 的配置**复制进 probe**，再 dump。
2. 见 5.1：删文件先于重启，导致内存/磁盘短暂不一致。

### 5.5 还剩一件事：GUI 里打开审批提示

方案 A 的前提。不开的话，越界写不是「询问」而是**自动拒绝**。开完之后：
日常在 workspace 内写零摩擦；动 `~/.dsh` 这类系统级路径才弹一次。

**降低摩擦的两个办法**（选一个）：
- 需要做系统维护的会话，在 GUI 里把该会话的权限预设切到 `danger-full-access`；
- 或把插件开发目录注册成工作区，让日常插件开发落在「工作区内」。
