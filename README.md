# DSH 体检（dsh-healthkit）

**升完级、改完配置，先问一句：插件还在跑吗？**

体检器最常用的时刻不是「有空体检一下」，而是**动过配置之后**：装/卸/升过插件、
改过 `cordis.patch.yml`、宿主要么起不来、要么某个插件静默不加载。这些时候你要的不是分数，
是「哪个还活着、哪个被静默跳过了」。没坏，才轮到看分数：
**一句结论 → 最值得动的 3 条 → 其余收进观测库。**

装完第一次跑，你会看到这样一段（真实输出，9.81 分的机器）：

```text
score=9.81/10 (raw 9.81, band 良好, P0=0, retired=3)

**整体健康，剩下的是打磨项**

最值得动的 3 条：
1. [P2] `R10` 高危扩展面未设白名单/黑名单 1 处
   → 逐项开通 allowlist/blocklist；无明确需求时保持空数组是显式接受风险
2. [P2] `R12` 插件声明了模型值，但无法静态核对运行时实际值（3 处）
   → 需在宿主内对照运行时注入值；静态审计只能标 UNKNOWN，不猜
3. [P2] `R16` 同时挂载 5 套记忆/上下文插件，每轮固定注入开销未量化
   → 需宿主内采样每轮注入 token；定主备后关掉其余自动注入

其余 14 条 INFO（不计分，观测用）：`audit_findings` 或 `--findings` 看全量。
```

### 动过配置之后：先看「还在不在跑」

DSH 是插件化的，升级或改配置之后最常见的坏法不是报错，而是**静默不加载**——
你看到的是「这个插件怎么不好使了」，宿主什么也没说。有四条规则专门盯这个：

| 规则 | 它抓什么 | 为什么这条能救你 |
| --- | --- | --- |
| `R23` | bundle 没声明 `dsh.bundle` | 宿主**静默跳过**，一条日志都不留 |
| `R1` | 依赖装了但没被 patch 挂载 | 包装了却从没生效过 |
| `R2` | `disabled` 指向的包不在依赖里 | 空转：以为关了，其实没关 |
| `R14b` | 装载日志里出现 `newly not running` | 宿主自己报过，但只躺在日志里 |

外加 `R22`（`file:`/`link:` 依赖目标已不存在）与**跨重启验回**（上次说该修的那几条，
这次回来看修好了没）。这几条合起来回答的才是「我动过配置，现在到底还行不行」；
分数是没坏的时候才看的。

### 两种用法：看状态，还是当 CI 门

- `audit_check`（或 `--check`）默认是**基线门**：只判「相对上一次快照的新增与回归」，
  存量问题不阻塞；新增少于 3 条 WARN 时不下判（照 SonarQube 的 fudge 口径），新增 FAIL 永不放过。
  想按绝对状态判，用 `--absolute`。
- `--check --remediation` 会附一份**有序**修法清单（`[规则号] 修法`），机器可读、缺席时字段不出现。

### 验回仪式（让它从「承诺」变成「证据」）

体检器最独特的能力是**跨重启验回**：上次说该修的三条，重启后回来看修好了没。
但它需要一次真实的回访才有数据——`audit_read`… 更准确地说：

1. 跑一次体检（会写下待验清单与快照）；
2. **真去修掉其中一条**；
3. 重启宿主（插件开机时自动验回）；
4. 看 `audit_digest` 或面板里的**结论采纳率**——它从 0 变成非 0，这条能力才算被证明过。

**它不做什么**（这是它最值钱的部分）：不改你的配置、不联网、不上传会话、不替你装/卸插件、
不提供「一键修复」——`cordis.patch.yml` 是整段替换，写错一个字段配置面就塌，而 82% 的发现
本身就没有确定修法。它给你**命令与顺序**，动手永远是你。
完整动作面（读什么、写什么、清理护栏）见 [SECURITY.md](SECURITY.md)。

### 它和 `dsh-plugin-doctor` / 插件管理器有什么不同

- **doctor** 查「单个插件是否合规」（三值 PASS/WARN/FAIL）；本插件查**整机**：跨插件冗余、
  装载面上限、上下文成本、磁盘卫生，以及「这些配置加起来是不是在拖慢你」。
- **插件管理器**只能开关；本插件给**修复顺序与预期涨幅**（先解 P0 封顶能涨多少）。
- 真正独有的是三件治理机制：**误报退役**（说错了能记档，且撤销得了）、
  **跨次三分账**（真修好 / 被静音 / 还在，静音不算修好）、**跨重启验回**
  （上次说该修的三条，重启后回来核对）。详见 [docs/COMPLEMENTARY.md](docs/COMPLEMENTARY.md)。

## 安装

```bash
# 发布版（npm）
dsh plugin --profile <profile> add dsh-healthkit

# 开发版（符号链接，改源码重启即生效）
dsh plugin --profile <profile> add link:/path/to/dsh-healthkit
```

开发期用 `link:`（符号链接，改源码重启宿主即生效）。`file:` 是拷贝，改源码不生效，
得 `dsh plugin --profile <profile> install --force` 重装。装完重启宿主一次。

## 十六个工具（查手册用，不必先读）

| 工具 | 干什么 |
| --- | --- |
| `audit_run` | 只读体检：总分、分档、P0/P1/P2 条数与清单（只读指不碰被检对象；记账本与快照可 record=false 关） |
| `audit_report` | 同上，并把完整 Markdown 报告写成文件（缺省落本会话工作区 `AUDIT-<日期>.md`） |
| `audit_clean` | 清理可再生垃圾：默认只预览，执行先移入回收区，7 天内可还原 |
| `audit_trend` | 分数历史：次数、最新分与变化、均值、最好/最差、P0 未关、sparkline |
| `audit_digest` | 差异驱动的周报摘要：与上次相比变了什么、上次说该修的现在怎样；没变化就一句话 |
| `audit_feedback` | 首次价值信号：这条发现我原先知不知道（只记本机、不外发），用来算首次价值率 |
| `audit_findings` | 问题清单（按严重度排序，带指纹与修法），可按 severity 过滤 |
| `audit_explain` | 解释某一条：维度、证据、测到的值、置信度、修法 |
| `audit_plan` | 修复顺序：先解 P0 封顶，再按单条增量排，给出全修完的终点 |
| `audit_trim` | 装载面瘦身：同能力多实现、超 bundles 上限、记忆插件叠放，给主备候选 |
| `audit_capabilities` | 能力域矩阵：20 个域 × 六态（有/多/冲突/失效/无/未知），每缺口给四级补救阶梯 |
| `audit_retire` | 误报记档（原因必填），之后不再计分；action=restore 撤销记档 |
| `audit_diff` | 跨次差异归因：新增了什么、真修好了什么、哪些只是被退役（不算修好） |
| `audit_verify` | 跨重启验回：上次体检说该修的，修好了没、有没有把别的东西搞坏（只报告不修） |
| `audit_check` | CI 门禁形态：PASS/WARN/FAIL 三值 + 退出码 0/1/2（与 dsh-plugin-doctor 同契约） |
| `audit_recommend` | 能力域推荐源：20 域的补救阶梯与「去哪找」（不联网、不给包名） |

不想用工具、只想在终端跑：

```bash
dsh-healthkit                 # 人读的报告（= node bin/audit.mjs）
dsh-healthkit --help          # 全部动作（不跑体检、不记账）
dsh-healthkit --json          # 机读
dsh-healthkit --why           # 每条问题修掉能涨多少
dsh-healthkit --trend         # 分数历史
dsh-healthkit --findings      # 问题清单 / --explain <fp> 解释一条 / --plan 修复顺序
dsh-healthkit --trim          # 装载面瘦身候选（只给建议，不改配置）
dsh-healthkit --init          # 接入自检：报环境/装没装/还差哪一步
dsh-healthkit --retire <fp> --reason "原因"   # 误报记档（--list-retired 查看）
dsh-healthkit --unretire <fp>                # 撤销记档（重新计分）
dsh-healthkit --diff              # 与上一次快照比：新增 / 真修好 / 新退役
dsh-healthkit --verify             # 验回：修好了没 / 还在 / 被静音 / 回归
dsh-healthkit --check              # CI 门禁：三值契约 + 退出码 0/1/2
dsh-healthkit --recommend          # 能力域推荐源（20 域阶梯 + 去哪找）
dsh-healthkit --format json       # 全量 JSON 报告（机器可读，schema: dsh-healthkit/report/v1）
```

## 面板

**原生侧边栏面板（推荐）**：装上并重启后，右侧栏会出现「体检」标签——总分、分档、
P0/P1/P2/INFO、未解决/已退役、可清理空间、服务插件水位、最新分与记账，以及按严重度排的前 8 条
（带修法提示与指纹）。走 `sidebarRightTabs` + `slots`，**不占端口、不用记地址、不经过 iframe**。

**独立网页（备用）**：`http://127.0.0.1:<宿主端口>/dsh-healthkit-panel`
（端口跟宿主 GUI 一致）。服务端渲染、页面零 JS、每 60 秒自刷新；数据接口
`/dsh-healthkit-panel/api/summary` 可程序化读取。

- 侧边栏的 iframe 浏览器**不执行页面脚本**，所以网页面板直接塞进侧边栏会空白——要么用原生标签，
  要么在系统浏览器里打开。0.5.3 起网页面板也改成了服务端渲染，禁脚本环境照样能显示。
- **只读**：GET 不记账、不写状态，浏览器预取/刷新都安全；每分钟缓存一次。
- **只认回环**：非 127.0.0.1/::1 的请求直接 403。
- 面板挂不上不影响工具面（降级成没有面板，结果写进 `plugin-status.json` 的 `panel` 字段）。

## 它量什么

分维度看：安全、一致性、装载整洁、模型成本、可维护性等。每条问题带指纹，修好记成
`verified`，下次不会又冒出来当新问题。

P0 会封顶总分（≥1 条封 5.0，≥3 条封 4.0）——所以分数涨得快，通常意味着 P0 真被修掉了，
而不是规则变宽松。

体检是**只读**的：不写配置、不联网、不读你的会话内容。

## 清理为什么敢按

- **永不直删**：一律进 `$DSH_HOME/dsh-healthkit/trash/<批次>/`，带 manifest，7 天内搬回原样
- **今天的备份绝不动**：`_backup` 只淘汰 ≥14 天的
- **护栏硬挡**：`node_modules` / `sessions` / `attachments` / `skills` / `data` / `.git` /
  credentials 一律拒绝；`apply` 必须给具体 ids，没有「全清」
- **需确认档**（远程工作区镜像）不给 `confirm` 就不动

真宿主 `failures: []`。

`docs/NOTES-host-contract.md`，修过的 bug 见 `docs/ISSUES.md`，
